## Index plan for this unit (approved plan, nothing more)

- `customers`: unique `_id` (= `cust_id`, implicit); `(conversion_batch_no)` for the
  BALANCES/RPT-114 rollup; `(tenant_id)`.

## Sequence and trigger replacement (coverage.md)

| Source object | Replacement in this unit |
|---|---|
| `SEQ_CUSTOMER_MASTER` | migrated rows keep source `cust_seq_no`; new writes get an app-generated monotonic long (no counters collection; census found no external consumer, and the source asserts no uniqueness — the PK is `cust_id`) |
| `SEQ_CUSTOMER_MASTER_HIST` | `ObjectId` for new history rows; migrated rows keep their numeric source `HIST_ID` (mixed `_id` types are intentional) |
| `SEQ_ENTITY_ATTR_VALUE` | migrated elements keep source `eav_id`; new attributes are keyed by `attr_name` |
| `TRG_CUSTOMER_MASTER_SEQ` | app-side write path: id assignment, `cust_name_upper = UPPER(cust_name)` (NULL stays NULL), `row_version_no` default 1 |
| `TRG_CUSTOMER_MASTER_HIST` | app-side full-row copy into `customer_master_hist` on update and delete, `hist_op` `UPD`/`DEL`, `hist_dt` in the legacy `'DD-MON-YY HH24:MI:SS'` English-month string shape, written in the same session/transaction as the mutation |
| `TRG_ENTITY_ATTR_VALUE_SEQ` | element key assigned at write time |

Application path: the `BALANCES_SQL` rollup behind `/api/reports/reconciliation`
(`services/legacy-billing/app/reports.py`) is rewritten as an aggregation pipeline over
`customers` (`$match` on `conversion_batch_no`, `$group` count + `$sum` of `cur_bal_amt`
and `past_due_amt`), with the legacy `TO_CHAR(x,'FM999999999999990.00')` rendering
reproduced exactly (2 decimals, half-up, no grouping; `SUM` over zero rows → null).
The month-end `STATUS_SQL`/`LINE_SQL` paths in the same file belong to U2 and are untouched.

## Load protocol

Idempotent by construction: every run drops and recreates `customers` and
`customer_master_hist` before inserting, then rebuilds the indexes above (engagement
convention, 05_decisions.md — M0 cannot make a multi-collection rename swap atomic).
Extract is a single serialized Oracle read (source-load cap 1). Oracle is read-only.

## Recon gate

`recon run --unit U1 --family oracle --mode live --seed 0` over the two collections, with
the mapping subset rendered verbatim from the approved spec. `result.json` is the only
merge authority. Child runs are `run_mode: fixture` self-checks against this VM's own
deterministic NS=demo fixture; the parent's uncontended run is the live proof.
Tier 3 runs as a **full keyed diff** (25,000 roots < the 100,000 threshold): every mapped
field of every root and every embedded element is value-graded, no sampling.

## Declared-unexercised / open risks (top of the PR body too)

- `CUSTOMER_MASTER_HIST` is empty at source (0 rows): the collection is created and graded
  empty. The history *write path* replacing `TRG_CUSTOMER_MASTER_HIST` is unit-tested only —
  no migrated row exercises it, and recon cannot grade an empty population.
- Harness Tier 4 (app-level parity replay) is not reachable from the `recon` CLI: the engine
  requires `run_source`/`run_target` callbacks the CLI does not expose. The `BALANCES_SQL`
  rewrite is therefore evidenced by a unit-owned side-by-side parity run
  (`scripts/tp_mongo/parity_balances_u1.py`, Oracle vs MongoDB, same shaped output),
  declared as unit evidence and NOT as a harness verdict.
- Tier 2 null semantics (identified before load, evidence in the PR): Oracle
  `COUNT(DISTINCT col)` excludes NULLs while MongoDB's distinct grouping counts the null
  group, and Oracle `SUM` over an all-NULL column is NULL while MongoDB `$sum` is 0. In the
  NS=demo population 19 Tier-2-graded columns are NULL-bearing (17 all-NULL:
  `PHONE3_TYPE_CD`, `PHONE4_TYPE_CD`, `TERRITORY_CD`, `CHANNEL_CD`, `RATE_CLASS_CD`,
  `LTD_BILLED_AMT`, `YTD_PAID_AMT`, `UDF_AMT_01..10`; 2 partial: `SUB_STATUS_CD`,
  `CREDIT_LIMIT_AMT`). No load-side representation satisfies both this comparison and the
  approved "source NULL → explicit BSON null, NULL ≠ missing" rule, so if the gate reports
  these they are reported as PROFILE FEEDBACK plus an explicit amendment request — never
  worked around in the load, and never by editing the tolerance record or a verdict.
